Why this is not a reporting project

Most analytics work describes data that some other system produced. If a row is wrong, that is upstream's problem.

This system is first in the chain. Nothing upstream will catch a bad row, so every rule a person would otherwise apply by judgment is written down as something the database will refuse. Each rule is proven by a test that asserts the refusal, not the happy path:

  • A shave-down cannot be recorded without a coat assessment that justifies it.
  • A haircut cannot be recorded on a bath-only visit.
  • A reminder cannot be sent to an owner who opted out.
  • A dog cannot start a groom while a required vaccine is expired, missing, or disputed.
  • A vaccination record cannot be created from a document that does not state an expiry date.

How strictly each groom-time rule is enforced (block, warn, or off) is itself a row of data, changed by an UPDATE and recorded in the audit log, not by a code change.

The document that proves the point

A real vet invoice for Jaddi, the dog whose grooming routine started this project, names a rabies vaccination and the date it was given. It contains no expiry date anywhere on the page.

The system keeps the document, keeps the extraction, and creates no vaccination record. It does not assume a one-year or three-year validity, because both are legal and the certificate is what the health department will actually see.

A pipeline that correctly declines to invent a date is a better result than one that extracts cleanly. Anyone can demo a clean extraction.

What the AI actually did

Vaccination paperwork is read by a vision model (Claude), then scored field by field against hand-labelled answer keys. Every run below is re-scored with the same ruler so the rows compare. Overconfident means a character the page prints but no one can read, returned as a clean, specific value: a smudged Jan 2?, 2027 read back as Jan 29, 2027.

On clean pages the model transcribes perfectly. On a phone photo of the same kind of page it makes the same mistake every time, whatever the prompt: about fifteen confident dates the page does not support. A third prompt did not fix it.

That is why the database does not trust a date just because it is present. A line becomes a vaccination record only after a person has checked every field it carries. A reviewer who can't read a date says so, which asks the owner for a better copy instead of recording a guess.

Try it yourself

The live demo is the groomer's check-in screen with the shop's real database running in your browser tab: PostgreSQL compiled to WebAssembly, loaded with the project's schema and invented demo dogs. Nothing is mocked. Every refusal you meet is the database's own, and nothing leaves your tab. A reload starts over. Things to try:

  • Jaddi: rabies expired, so the groom is refused.
  • A new walk-in client whose paperwork has no expiry date: no expiry, no record.
  • Booking a regular client with a different groomer: it asks why.
  • Recording a shave-down of a pelted coat: the coat assessment decides whether it is allowed.

The admin view, dog and paperwork photos, and the AI reader need a server, so they are left out of the browser demo.
